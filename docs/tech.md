# 技術の定義（第5版。段階0から6を作ったあとの実物に合わせた）

「何を使って、どう作るか」を決めます。
決めた理由も書いておきます。あとで変えるときに、理由ごと見直せるようにするためです。

## 1. 全体の形

- 1つのWebアプリに、スマホの画面、表紙の画面、管理の画面をまとめる。
- 画面とサーバーの両方をTypeScriptで書く。
- サーバーが3社のAIを呼ぶ。スマホから直接AIを呼ばない（APIキーを人に見せないため）。
- 本文は保存しない。判定が終わったら捨てる。

```
スマホ ──→ サーバー ──→ Anthropic（蔵人）
   ↑           │    ──→ Google（二ナ）
   │           │    ──→ OpenAI（ソル）
   │           ↓
   │       データベース（作品名、作者名、判定など。本文は入れない）
   │           ↑
MacBookの表紙 ─┘（10秒ごとに読みに来る）
```

## 2. 使うもの

| 役割 | 使うもの | 理由 |
|---|---|---|
| 画面とサーバー | Next.js（App Router）とTypeScript | 画面とサーバーを1つのコードにまとめられる。置き場所の選択肢が多い |
| 見た目 | 素のCSS（app/globals.css） | モックのCSSをそのまま引き継ぐため。Tailwindは使わない |
| 置き場所 | Vercel | Next.jsをそのまま置ける。当日だけの公開なら無料の範囲で足りる |
| データベース | Neon（Postgres）。手元ではPGlite | 本番はVercelのStorageから作れる。手元は同じPostgresの形で data/pglite に保存する |
| データベースの操作 | SQLを直接書く（lib/db/index.ts） | 表が5つしかないので、道具を増やさない。表は最初のアクセスで自動で作る |
| 蔵人 | Anthropic公式SDK（@anthropic-ai/sdk） | モデルはclaude-sonnet-5（当日）、claude-haiku-4-5（試験中） |
| 二ナ | Google公式SDK（@google/genai） | モデルはGemini 3.7 Flash（正確なID名は実装時に確認） |
| ソル | OpenAI公式SDK（openai） | モデルはgpt-5.6-luna |
| 結果の画像 | Next.jsの画像生成（next/og） | 結果のURLをXに貼ったときに出る画像。日本語フォントはNoto Serif JPとNoto Sans JPを同梱する |
| 大画面の表紙 | three.js | 格子の床の上に浮かぶ3誌の表紙。スマホでは使わない（docs/design.md 第3版の5を参照） |
| スマホの動き | CSSアニメーションと端末の傾きセンサー | 投函、読まれていく文字、判子、部屋の奥行き。3Dライブラリは使わない |
| QRコード | qrcode（npm） | 表紙の隅に出す |

Vercel、Neonは、あなたのアカウントで作ってもらう。
私はコードを書き、置く手順を書く。

### 使わないと決めたもの

- 画像生成AI。文字が崩れるので使わない。表紙も結果の画像もプログラムで描く。
- 本物の順番待ちの仕組み（キュー）。作りが重くなる。代わりに「混んでいたら少し待って自動でやり直す」で済ませる（7を参照）。
- 会員登録やログイン。来場者には要らない。管理画面だけ合言葉で守る。

```
app/

  r/[id]/opengraph-image.tsx  結果の画像（X用）
  cover/page.tsx           表紙（3誌を切り替え、下に目次）

  admin/page.tsx           管理
  api/
    submit/route.ts        原稿を受け取って判定を返す

    stats/route.ts         今日の傾向を返す
    r/[id]/status/route.ts いまの掲載を返す
lib/
  editors/
    kurodo.ts              蔵人の指示文と癖の一覧
    nina.ts                二ナの指示文と癖の一覧
    sol.ts                 ソルの指示文と癖の一覧
    common.ts              3人に共通する土台の文
  providers/
    anthropic.ts           Anthropicを呼ぶ
    google.ts              Googleを呼ぶ
    openai.ts              OpenAIを呼ぶ

  judge.ts                 判定の流れ全体（事前チェック → AI → 検算 → 保存）
  precheck.ts              AIを呼ぶ前のチェック（長さ、禁止語、重複、回数制限）

  fonts/                   Noto Sans JP
```

## 4. データベースの表

本文は入れない。これが一番大事な決まりです。

### submissions（持ち込みの結果）

| 列 | 型 | 中身 |
|---|---|---|
| id | 文字列 | 結果の番号。URLに使う短いランダムな文字列（例: ab12cd） |
| editor | 文字列 | kurodo / nina / sol |
| pen_name | 文字列 | 作者名（10字まで） |
| placement | 文字列 | kanto（巻頭）/ tokushu（特集）/ kanmatsu（巻末）/ namae（名前だけ）/ jigo（次号待ち） |
| score | 整数 | 点数。判定の土台（400/300/200/100/0）に、AIが返す細かい点（0から100）を足したもの |
| device_id | 文字列 | 端末の目印。最初に開いたときにクッキーで配る乱数 |
| is_sample | 真偽 | 見本の原稿で試した結果なら真。表紙にも目次にも載せない |
| revision | 整数 | 同じ端末から同じ雑誌への何回目か。1回目は1 |
| prev_id | 文字列 | 改稿のとき、前回の結果の id |
| title | 文字列 | 作品名 |
| quote | 文字列 | 引用した一文 |
| comment | 文字列 | 編集者のコメント |
| next_request | 文字列 | 次に持ってきてほしいもの |
| reason_tags | 文字列の配列 | 理由の札 |
| work_type | 文字列 | 日記、手紙、小説、詩、つぶやき、AI、コピペ |
| safe_for_cover | 真偽 | 表紙に載せてよいか |
| hidden | 真偽 | 管理画面で「表紙から外す」を押したら真 |
| issue | 文字列 | 号。イベントの月（例: 2026-10）。1日1冊 |
| created_at | 日時 | 作った時刻 |

### settings（設定）

| 列 | 中身 |
|---|---|
| key | accepting / daily_cap / event_tweet_url / editor_kurodo_open / editor_nina_open / editor_sol_open / published_at（発行した時刻。空なら組版中） / strictness_kurodo / strictness_nina / strictness_sol（甘め、ふつう、厳しめ） |
| value | 文字列 |

### throttle（回数の記録）

| 列 | 中身 |
|---|---|
| bucket | 何の回数か。例: day:2026-10-05、ip:（端末の目印）:hour:13、provider:google:min:1342 |
| count | 回数 |
| expires_at | いつ消してよいか |

### afterwords（編集後記）

| 列 | 中身 |
|---|---|
| editor | kurodo / nina / sol |
| body | 編集後記の本文（200字ほど） |
| created_at | 書いた時刻 |

### text_hashes（重複よけ）

| 列 | 中身 |
|---|---|
| hash | 本文のハッシュ値（本文そのものは入れない） |
| expires_at | 24時間で消す |

## 5. 判定の流れ

`POST /api/submit` に、編集者、ペンネーム、本文が来る。

1. 受付中か、上限に達していないかを settings と throttle で見る。
   だめなら「受付終了」を返す。
   見本の原稿（is_sample）なら、同じ端末から1回だけ受け付ける。
2. 事前チェック（precheck.ts）。AIを呼ぶ前に済ませる。
   - 本文が20字以上1000字以下か。
   - ペンネームが1字以上10字以下か。
   - 禁止語が含まれていないか（一覧はコードの中に置く）。
   - 同じ本文のハッシュが24時間以内にないか。
   - 同じ端末から1時間に5回を超えていないか（端末の目印はIPアドレスとブラウザの情報のハッシュ）。
   - その編集者が出勤中か。
   - 有名作品の冒頭に当たっていないか（lib/famous.ts）。当たったらAIを呼ばず、決まった結果を返す。
   だめなら理由つきで返す。AIは呼ばない。
3. 癖を選ぶ。その編集者の癖4つから、1つか2つをランダムに選ぶ。
   改稿かどうかを見る。同じ device_id と editor の今日の結果があれば、その作品名、判定、次のお願いを「前回」として渡す。
   厳しさの一文（settings）と、今日ここまでのその編集者の判定の割合（直近50件）を1行ずつ足す。
4. AIを呼ぶ（providers/）。
   - 固定の指示文（system）: 共通の土台 + その編集者の性格と見るところ + 返す形の説明。
   - 毎回の入力（user）: ペンネーム、本文、今回の癖。
   - 返す形は決まった形のデータ（JSON）に固定する。3社とも、決まった形で返させる機能を使う。
   - 待ち時間の上限は25秒。超えたらエラー扱い。
5. 検算（judge.ts）。
   - quote が本文に本当に含まれているか。含まれていなければ quote を空にする。
   - placement が5つのうちのどれかか。違えば「巻末」に倒す。
   - title が15字以内か。長ければ切る。
   - 細かい点が0から100の整数か。違えば50にする。
   - comment が300字以内か。長ければ切らずにそのまま出し、指示文を直す材料にする（記録だけ残す）。
   - safe_for_cover が偽なら hidden も真にする。
6. 点数を決める（judge.ts）。判定の土台に細かい点を足して score にする。
7. submissions に保存する。本文は保存しない。
8. 結果を返す。画面はそれを上から順に出す。

## 6. AIに返させる形

3社とも、この形で返させる。

```json
{
  "work_type": "日記",
  "placement": "tokushu",
  "title": "飲まないまま",
  "title_alt": "",
  "quote": "飲まないまま持って帰った",
  "comment": "先に言っておくと、……だから特集にします。……",
  "next_request": "今回のように、理由を書かないで終わる話をもう1本お願いします。",
  "reason_tags": ["理由を書かずに終わる", "入りがありふれている"],
  "safe_for_cover": true
}
```

- title_alt は二ナだけ使う（作品名を2案出して迷うため）。
- reason_tags は、あらかじめ決めた一覧から選ばせる。一覧は lib/editors/common.ts に置く。

## 7. 混んだときの扱い

本物の順番待ちは作らない。代わりにこうする。

- 会社ごとに1分あたりの回数を throttle で数える。上限は会社ごとに設定（有料の枠に合わせる）。
- 上限に当たったら、サーバーは「混んでいます。N秒後にもう一度」と返す。
- スマホ側は「前に何人かいます。少しお待ちください」と出して、N秒後に自動でもう一度送る。
  本文はスマホの中に持ったままなので、貼り直しは要らない。
- 3回やり直してもだめなら「時間をおいてもう一度」と出す。

## 8. 表紙と目次（1冊にまとめる）

雑誌は3誌（季刊フェーブル、週刊フラッシュ、月刊アストラ）で、編集者と1対1なので、雑誌の欄は持たず editor で見分ける。
表紙の枠は1誌に10（巻頭1、特集3、巻末6）、全部で30。
表紙に載る作品は保存せず、そのつど計算する（cover.ts）。

1. その日の submissions のうち、hidden でなく、placement が kanto / tokushu / kanmatsu のものを集める。
2. 雑誌ごとに、同じ device_id、または同じ pen_name の結果は、score が一番高い1作だけ残す（1誌につき1人1作）。
3. 雑誌ごとに score の高い順に並べ、上から巻頭1、特集3、巻末6に入れる。
4. あふれた作品と、placement が namae の作品は目次に載る。目次は作者名と作品名の一覧で、新しい順。
5. settings の published_at が入っていたら、その時刻までの結果だけで計算する（発行後は変わらない）。

- 表紙の画面は10秒ごとに `GET /api/cover` を読みに来る。返すのは3誌それぞれの10枠と目次の一覧。本文もコメントも返さない。
- 結果のページは `GET /api/r/{id}/status` でいまの掲載（どの雑誌のどの枠か、目次か、未掲載か）を取る。
- `GET /api/stats` は今日の傾向（理由の札の集計、判定の割合、持ち込み数）を返す。入口と大画面が使う。
- 発行（管理画面の「表紙を固める」）のとき、3人ぶんの編集後記を作って afterwords に入れる。
  材料は今日の持ち込み数、表紙に載った作品名、多かった理由の札。AIを呼ぶのは1日に3回。
- 新しく表紙に入った作品と、表紙から目次に下がった作品は、画面側で1回だけ光らせる。

## 9. Xへの投稿

- 「Xに投稿する」は、Xの投稿画面を開くURLを組み立てるだけ。サーバーはXと通信しない。
- 文の形: 「AI編集部の{雑誌}に持ち込んだら、{編集者}が{判定}にしてくれました。作品名『{作品名}』 #AI編集部 {結果のURL} {告知ツイートのURL}」
- 結果のURLを開くと出る画像は next/og で描く。雑誌の色の地に、六角形の印、作品名、作者名、雑誌名、編集者の顔。日本語フォントを同梱し、中国語の字体が混じらないようにする。

## 10. 管理画面

- `/admin` は合言葉（環境変数 ADMIN_PASSWORD）で守る。
- できること: 受付中と受付終了の切り替え、上限回数、告知ツイートのURL、編集者ごとの出勤と休業、表紙と目次から外す、発行（表紙を固める）、今日の回数とエラー回数を見る。

## 11. 環境変数

| 名前 | 中身 |
|---|---|
| DATABASE_URL | Neonの接続先 |
| ANTHROPIC_API_KEY | 蔵人 |
| GEMINI_API_KEY | 二ナ |
| OPENAI_API_KEY | ソル |
| ADMIN_PASSWORD | 管理画面の合言葉 |
| APP_URL | 公開先のURL（結果のURLと投稿文に使う） |
| MOCK_EDITORS | 「1」にすると、AIを呼ばずに例の結果を返す。キーがない間の開発用 |

## 12. APIキーがなくても動かす

`MOCK_EDITORS=1` のとき、providers/mock.ts が docs/samples.md と同じ結果を返す。
これで、画面、表紙、管理、投稿の導線を、キーなしで最後まで作って確かめられる。
キーが届いたら、環境変数を入れるだけで本物に切り替わる。

## 13. 作る順番

1. Next.jsの土台を作る。空の画面9つと、表の定義。
2. mock で判定の流れを通す。入口から結果までスマホで動くようにする。
3. 表紙を作る。号の分け方まで。
4. 管理画面を作る。
5. 結果の画像（X用）を作る。日本語フォントを確かめる。
6. 3社の呼び出しを作る。キーが届いた編集者から順に試す。
7. テスト用の原稿の束（docs/concept.md の7）を3人に見せて、結果を並べて見る。
8. 指示文を直す。
9. Vercelに置いて、スマホで通しで確かめる。

## 14. 決まったこと

- 雑誌を選ぶ画面に「中身: Claude」のように会社名を小さく出す。
- 1つの端末からの回数は1時間に5回まで。
- 顔と部屋の絵は、まず仮の絵で作り、あとから画像生成AIで作ったものに差し替える。

## 15. まだ決めていないこと

1. 「次号待ち」の作品は表紙にも目次にも出ない。管理画面の「最近の結果」にだけ出る。それでよいか。
2. 端末の目印をクッキーにするか、ブラウザの保存領域にするか。クッキーのほうがサーバーで扱いやすい。
